# Crosslinking Architecture — Evidence-Aware Derived Navigation

**Status:** Implemented (2026-08-09) · **Owner module:** `scripts/crosslinks.py`
**Validation:** `scripts/validate_crosslinks.py` · **Docs:** this file,
`reports/crosslinking-implementation.md`, `docs/graph/coa-lab-data-model.md`,
`docs/cultivar-identity-model.md`

---

## 1. Purpose and core principle

The archive accumulates entities across twenty-five collections. Manually
maintaining crosslinks between them does not scale: adding one laboratory
report should not require editing nine unrelated pages. This layer makes
**relationships data and links presentation**:

1. Structured relationships live in the sources the site already publishes
   (frontmatter `relations:`, the cultivar claim registry, durable COA
   records).
2. A deterministic derivation pass turns those relationships into labeled,
   bounded navigation sections.
3. The renderer (Boris) stays the single graph engine. This layer does **not**
   reimplement discovery, parent/nav validation, or rendering; it consumes
   validated structured data and adds presentation edges only.

Nothing here is a keyword-linking bot: no word is ever replaced in prose, and
no entity page is created just because a name exists.

## 2. Structured relationship sources

| Source | File(s) | What it provides |
| --- | --- | --- |
| Semantic relations | `content/**/*.md` frontmatter `relations:` | Author-declared, Boris-validated relations (`relates_to`, `implements`, `depends_on`, `supersedes`) |
| Cultivar identity claims | `metadata/cultivar-claims.jsonl` | Typed identity/claim edges with provenance (`product_claims_cultivar`, `batch_claims_cultivar`, `claimed_lineage_parent`, `claimed_bred_by`, `listed_by`, `sold_by`, aliases, …) |
| Durable COA records | `metadata/coa-records.jsonl` (one `CoaRecord` per line, schema `metadata/coa-measurement.schema.json`) | Measurement edges: report → laboratory (`tested_by`), report → batch, batch → product, batch cultivar labels, report → compound (`analyte_result`) |
| Entity registry | `metadata/id-map.jsonl` (generated by `scripts/ted_ids.py`) | Entity ids → titles, collections, rendered output paths |

The canonical entity model:

```text
LabReport ──tested_by──▶ Laboratory
    ├──batch──▶ Batch ──product──▶ Product ──cultivar_claim──▶ Cultivar
    ├──analyte_result──▶ AnalyteResult ──analyte──▶ Compound (terpene / cannabinoid / contaminant)
    └──jurisdiction──▶ Jurisdiction
Cultivar ──claimed_bred_by──▶ Organization/Breeder   (claim registry, entity or named source)
```

## 3. Edge classes

Every generated link carries exactly one edge class; classes are never mixed
and never silently upgraded:

| Class | Meaning | Sources | Never used for |
| --- | --- | --- | --- |
| `direct` | Author-declared semantic relation | frontmatter `relations:` | anything not in the closed Boris vocabulary |
| `source` | Provenance/attribution to a named non-entity (e.g. a breeder with no page) | claim registry `object_is_entity: false` | links — rendered as labeled text, never a hyperlink to a nonexistent page |
| `measurement` | A COA measurement edge | `metadata/coa-records.jsonl` | statistical claims (record kind gates analysis) |
| `identity_claim` | A claim-registry edge with an entity object | claim registry `object_is_entity: true` | a factual assertion — it stays "X claims Y" |
| `derived` | Reverse navigation or multi-hop projection with an evidence trace | computed from the forward classes | primary evidence — always carries `trace` and renders with its source class |

The invariant enforced by validation: a `derived` edge is never emitted as a
primary factual assertion, and no `derived` edge exists without an evidence
trace.

---

## 4. Reverse-edge strategy

Every forward edge has an automatic reverse navigation edge (class `derived`)
with the forward edge's id as its trace. Example:

```text
Report ──tested_by──▶ Laboratory        (measurement, forward)
Laboratory ──issued──▶ Report           (derived, reverse, trace = [Report])
```

This replaces the manual "bidirectional pair" convention from the earlier
connectivity pass: there is no longer any need to edit both ends of a
relationship, and graph disagreement from double-maintained edges cannot
arise. Reverse edges are presentation only — the laboratory page's "Reports
issued" section is navigation, not a claim that the laboratory asserted
anything.

## 5. Derived-edge strategy (multi-hop projections)

Some navigation is genuinely useful but must never become a permanent factual
assertion. The canonical example:

```text
Cultivar ← claimed by Product ← Batch ← LabReport → AnalyteResult → Compound
```

The layer derives `Cultivar → Compound` as a `derived` edge whose **trace is
the set of reports** that measured the compound in a batch carrying the
cultivar label. The UI renders it as:

> **Compounds observed in associated reports** — "These observations are
> batch- and report-attached; they do not assert that a cultivar name implies
> a fixed chemistry."

It never renders "Blue Dream contains myrcene." The same discipline applies to
`Product → Compound`, `Compound → Cultivar`, and `Compound → Product`
projections: every one carries its justifying report ids.

Other multi-hop projections that are derived (with traces):

| Projection | Trace | Why it is derived, not direct |
| --- | --- | --- |
| Cultivar → compounds | report ids | batch/report-attached observations |
| Compound → cultivars | report ids | the cultivar name is a label, not a chemotype |
| Product → compounds | report ids | batch/report-attached observations |
| Compound → products | report ids | the product is a label carrier, not a chemistry assertion |

## 6. Rendering rules

Sections are context-appropriate per role (compound, cultivar, product,
laboratory, lab report) plus generic `related` (outgoing direct relations)
and `backlinks` ("Pages that link here", reverse of direct relations):

| Role | Derived sections (in order) |
| --- | --- |
| Compound (terpene/cannabinoid/contaminant) | Laboratory reports measuring this compound · Products with measurements · Cultivars observed in associated reports · Botanical occurrence (direct) · Related · Backlinks |
| Cultivar | Lineage · Breeder / origin claims · Seed / catalog listings · Aliases & identity · Products carrying this name · Batch-associated laboratory reports · Compounds observed in associated reports · Related · Backlinks |
| Product | Cultivar claim · Laboratory reports · Compounds observed in associated reports · Related · Backlinks |
| Testing laboratory | Reports issued · Related · Backlinks |
| Lab report | Testing laboratory · Batch · Product · Cultivar claim · Measured compounds · Related · Backlinks |
| Everything else | Related · Backlinks |

Rendering rules:

- **Bounded.** At most `MAX_ITEMS_PER_SECTION` (8) links per section and
  `MAX_LINKS_PER_PAGE` (48) generated links per page. The full reproducible
  count is always shown ("18 associated reports"). When a section exceeds the
  display cap, the entity page links to dedicated paginated index pages
  ("View all 18") instead of truncating with "(+N more)". Index pages are
  generated at `INDEX_PAGE_SIZE` (100) items per page, live next to the
  entity page (same URL depth, so relative links stay valid), carry
  `data-crosslinks-index` / `data-index-for` / `data-index-section` markers
  plus a prev/page/next pager, and link back to the entity page. No page ever
  renders 20,000 backlinks.
- **Labeled.** Each section and item carries `data-edge-class` and
  `data-source-class`; record kinds (e.g. `demonstration`, `unverified`) are
  badges on the link so demo records stay visibly non-evidence.
- **Deterministic.** Sections are ordered by a fixed rule table, items by
  (evidence weight, entity id). Regenerating over the same inputs yields
  byte-identical output.
- **Traceable.** Every derived link shows the record count behind it and
  carries the report ids in the machine export, so a reader (or a machine)
  can answer *why is this terpene linked to this cultivar?* — because
  reports A/B/C measured it in batches of products carrying that cultivar
  claim.
- **Non-invasive.** Sections are injected after the Boris render into the
  generated HTML (idempotently replacing a previous run's block), never into
  content files. The content tree stays the source of truth.
- **Crawlable.** Injected links are plain internal HTML links (SEO-visible)
  but only ever point at real entity pages — no doorway pages.

## 7. RAG / IR / Context rules

Machine consumers must be able to tell the epistemic weight of every link.
The deterministic machine export `exports/crosslinks.json` (written by
`scripts/crosslinks.py --out`, gitignored like other generated exports)
preserves the distinctions:

```json
{
  "schemaVersion": "1.0",
  "edgeClassCounts": {"derived": 677, "direct": 672, "identity_claim": 5},
  "entities": [{
    "id": "terpenes/TTRP-0005",
    "sections": [{
      "key": "measured_reports",
      "label": "Laboratory reports measuring this compound",
      "edgeClass": "derived",
      "sourceClass": "measurement",
      "count": 1,
      "items": [{"id": "lab-results/TLAB-0001", "title": "...",
                 "trace": ["lab-results/TLAB-0001"],
                 "recordKinds": ["demonstration"]}]
    }]
  }]
}
```

Rules for RAG consumption:

1. Join Boris's RAG/IR exports with `crosslinks.json`; never re-derive.
2. Prefer the **source class** (`measurement`, `identity_claim`, `direct`)
   over the display class when grading a statement.
3. Derived associations must be phrased epistemically. The RAG companion
   (`exports/crosslinks-rag.md`) ships the approved wording, e.g.
   *"Myrcene appears in laboratory reports associated with products labeled
   Blue Dream"* — never *"Blue Dream contains myrcene."*
4. `recordKinds` gate any statistical use: only `verified` records are
   analysis data (demonstration/unverified are navigation-only and are
   badged as such).
5. Context bundles should include the edge-class legend (this document §3)
   so downstream models treat `derived` edges as navigation, not facts.

## 8. Performance

- Indexes are built **once** per run: entity lookup O(1), adjacency maps
  (outgoing/incoming per entity) O(1) per query, claims and COA edges in
  O(E) total.
- Multi-hop projections are computed over sorted sets of report/compound ids,
  not nested per-page scans.
- Per-entity section derivation is O(degree) lookups plus bounded truncation;
  there is no O(N²) relationship expansion anywhere in the hot path.
- Output is bounded by construction (section caps), so cost does not grow
  with the number of backlinks a page has.
- 413 entities / 1,354 edges / 313 injected pages on the live build; the
  entire `ted-build.sh` (Boris compile + audits + injection) runs in ~19 s
  locally, with the crosslink pass adding well under a second.

## 9. Scale limits and future work

Designed for hundreds of thousands of measurements, tens of thousands of
reports, and thousands of products/batches:

| Limit today | Bound | Notes |
| --- | --- | --- |
| Items per section | 8 (configurable constant) | dedicated paginated index pages beyond this |
| Links per page | 48 | dedicated collection indexes with count links |
| Index page size | 100 (configurable constant) | one index page per section per 100 items |
| Trace size per item | 3 report ids (with total count) | summary-only traces on index pages |
| Machine export | full (bounded) section lists | queryable JSONL endpoint per collection |

Built and verified:

- Dedicated generated index pages per high-degree relationship (e.g. "all
  reports for laboratory X") are generated automatically whenever a section's
  count exceeds `MAX_ITEMS_PER_SECTION`; the entity page links to them
  instead of truncating. Verified by CXL-11/CXL-12 (see §10).

Future scaling work (documented, not built):

- Moving the machine export to per-collection JSONL for incremental
  retrieval at scale.
- Optionally retiring the hand-written "Related pages" lists in content once
  the generated sections are stable (they are additive today and do not
  conflict — generated sections carry distinct markup).

## 10. Validation

`scripts/validate_crosslinks.py` (wired into `bin/validate_graph.sh` and
`scripts/ted-build.sh`) enforces:

| Code | Check |
| --- | --- |
| CXL-01 | Broken generated links (rendered HTML targets exist) |
| CXL-02 | Relations to nonexistent entity IDs |
| CXL-03 | Incorrect relation types (analyte→compound, tested_by→laboratory, product_of→product, cultivar claims→cultivar, lineage/breeder endpoints) |
| CXL-04 | Duplicate edges / duplicate generated navigation targets |
| CXL-05 | Derived edges presented as direct facts (or direct-class edges with non-frontmatter kinds) |
| CXL-06 | Derived edges without an evidence trace |
| CXL-07 | Frontmatter relations targeting nonexistent pages (mirrors Boris's own check for graph-only runs) |
| CXL-08 | Unbounded page expansion (section caps) |
| CXL-09 | Duplicate targets within one generated section |
| CXL-10 | Unknown edge classes |
| CXL-11 | Every section over the display cap has its index page(s), marked for the right section, at most `INDEX_PAGE_SIZE` items each |
| CXL-12 | The entity page links to the index (crawlable, not orphaned) |

Plus determinism and Definition-of-Done regression tests in
`tests/test_crosslinks.py`.

## 11. Definition of Done

Adding ONE new legitimate lab report (a `CoaRecord` in
`metadata/coa-records.jsonl` plus its content page, per
`docs/graph/coa-migration.md` Path A) with a cultivar claim, laboratory,
batch, THCA, Δ9-THC, β-myrcene, and limonene must automatically improve
navigation from:

`the report · the batch · the product · the laboratory · the cultivar ·
THCA · Δ9-THC · β-myrcene · limonene`

without manually editing nine unrelated pages. This is verified by
`tests/test_crosslinks.py::TestDefinitionOfDone` (fixture site) and holds by
construction on the live tree the moment the first verified record lands.
